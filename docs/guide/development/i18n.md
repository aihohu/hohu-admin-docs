# Internationalization

Built-in text uses stable translation keys rather than duplicating business records for each installation language. User-entered branding, names, agreements and business content remain unchanged.

## Built-in records

Menus use `i18n_key`; roles and Agents use `i18n_keys` metadata. APIs provide original text and translation metadata. Clients localize display without submitting translated labels to edit APIs. Editing a name or description removes its translation binding; repeated seeds must not rebind explicit customizations.

Older records receive keys only where text still matches built-in defaults. Language precedence is user choice, tenant default, then deployment `DEFAULT_LOCALE`. Missing translations fall back to English and original text.

## Add a language

1. Register it in the client locale registry and language selector.
2. Supply matching keys in ordinary UI, `builtin-*` and `settings-*` resources and update completeness tests.
3. Register the same language code in backend default-language options and adjust deployment defaults if needed.
4. Verify switching, built-in table labels, missing-key fallback, custom names and repeated initialization.

No second set of seed data or language-specific business IDs is needed. Translate errors using stable `errorCode`, not backend msg as a resource key. Multilingual business content is a separate product feature, not implicit rewriting by UI localization.
