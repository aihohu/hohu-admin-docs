# 升级、备份与恢复

升级前记录当前后端、Web、CLI、镜像和数据库迁移版本。确认目标版本的发布说明，不用 `latest` 代替可追溯的版本记录。

## 升级顺序

1. 备份数据库、私有文件及必要部署配置，并验证恢复方法；备份访问权限与生产凭据同等保护。
2. 在隔离环境演练升级，暂停生产写入与相关后台任务，安排维护窗口。
3. 使用配套 CLI、后端和 Web。源码构建使用 `hohu build` 后 `hohu deploy`；官方镜像更新可使用 `hohu deploy pull`，当前实现会迁移并同步基础数据后再启动。
4. 核对迁移退出码和服务状态，再验证登录、租户状态、权限拒绝、设置、上传与后台任务。
5. 确认结果后恢复流量，并保留本次版本与验证记录。

独立 `hohu migrate` 也执行迁移及种子同步，不再使用 `--init`。不要使用 `--no-migrate` 跳过实际必需的结构或数据更新。

## 支持的数据库起点

当前迁移支持空库和 v0.1.4 发布边界 `bf244f9a8b76`；更早版本先沿对应旧发布链升级。曾运行压缩前实验迁移的开发库不属于自动升级保证范围，不得仅执行 `stamp head` 伪装成已升级。

准确 head 以本版本 Alembic 输出为准。维护者约束见后端仓库 `docs/DATABASE-MIGRATIONS.md`，源码入口见[源码页](../src)。

## 恢复

切回旧代码不自动恢复数据库。破坏性 downgrade 可能删除新字段或表，不能替代备份恢复。失败后保持维护状态，先恢复匹配的数据库、持久文件和应用版本，验证后再恢复写入。

`hohu deploy upgrade` 包含源码拉取、构建、停止及重新部署，不是无停机更新，也不自动替你完成备份或解决本地源码冲突。
